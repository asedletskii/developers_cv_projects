## Как читать таблицы полей

В таблицах ручек пять колонок: **поле, тип, обязательное, ограничения, дефолт при создании**.

| В колонке «Дефолт» | Значит |
|---|---|
| `—` | Дефолта нет: поле обязательное, клиент обязан передать значение. Без него запрос отклоняется (`400`) |
| `отсутствует` | Поле необязательное. Если не передать, оно не сохраняется, а в ответах `GET` ключ просто не приходит (`null`/пропуск, не пустая строка) |
| `[]`, `""`, `false`, число | Поле необязательное, при создании получает именно это значение и приходит в ответах |

Колонка «Обяз.»: `да` — без поля запрос отклоняется, `нет` — поле можно опустить. Там, где значение зависит от других полей (например, «нужен хотя бы один контакт»), это написано в ограничениях.

## Базовые правила

**Адрес.** Все пути ниже — от `/api/v1`. В проде запросы идут на тот же origin (Caddy проксирует `/api` на бэкенд), локально — через прокси Vite.

**Авторизация.** Всё под `/lk/*` требует заголовок `X-Mock-User-ID: <uuid пользователя>`. Пока это заглушка: пользователь должен существовать в таблице `users` (сидовые: `10000000-0000-0000-0000-000000000001` и `…0002`). Нет заголовка, не UUID или неизвестный пользователь → `401 UNAUTHORIZED`. `GET /cv/:resumeId` авторизации не требует.

**Владение.** Резюме и его вложенные записи доступны только владельцу. Чужой или несуществующий `resumeId` (и вложенный id) даёт `404`, а не `403`.

**Идентификаторы.** UUID. `resumeId`, не являющийся UUID → `400 Invalid resume id`. Идентификаторы записей создаёт бэкенд, клиентские `id` в теле запроса не принимаются.

**Тело запроса.**
- JSON, кодировка UTF-8, `Content-Type: application/json`, не больше 1 МиБ (иначе `413 REQUEST_TOO_LARGE`).
- Строгий разбор: **любое неизвестное поле → `400 Invalid request body`**, как и второй JSON-значение в теле. Поэтому лишние поля (`id`, `resumeId`, `updatedAt`, `position` у языков и технологий) слать нельзя.
- Строки обрезаются по краям (`trim`). Пустая после обрезки строка считается пустой: у обязательных полей это ошибка `400`, у необязательных — то же, что отсутствие.
- **`PUT` — полная замена.** Поля, которых нет в теле, сбрасываются (необязательные) или дают `400` (обязательные). Частичного обновления нет.
- Пустой массив допустим и означает «список пуст»; отсутствующий массив читается так же.

**Форматы.**

| Формат | Пример | Где |
|---|---|---|
| Дата `YYYY-MM-DD` | `1998-04-12` | `dateOfBirth`, `availability.from` |
| Год-месяц `YYYY-MM` | `2020-01` | `startDate`/`endDate` опыта, `endDate` курса, `date` активности |
| Год `YYYY` | `2024` | `endDate` образования |
| Ссылка | `https://example.com/a.png` | только `http`/`https` с хостом; относительные пути отклоняются |
| Цвет | `#E8785A`, `#e85` | `#RGB` или `#RRGGBB` |
| Время | `2026-09-26T08:00:00Z` | `createdAt`, `updatedAt` (RFC 3339, UTC) |

**Ответы на запись.** `POST` → `201 {"id": "<uuid>"}`; `PUT` и `DELETE` → `204` без тела. Чтобы получить актуальное состояние, фронтенд перечитывает `GET /lk/resume/:resumeId`.

**Ошибки.** Тело всегда такое:

```json
{ "error": { "code": "BAD_REQUEST", "message": "Invalid request body", "requestId": "c16dd04d-…" } }
```

| Статус | `code` | Когда |
|---|---|---|
| 400 | `BAD_REQUEST` | неверное тело, неизвестное поле, нарушено ограничение поля (в `message` — причина) |
| 401 | `UNAUTHORIZED` | нет или неверен `X-Mock-User-ID` |
| 404 | `NOT_FOUND` | резюме или запись не найдены либо чужие; маршрут не существует |
| 409 | `CONFLICT` | дубликат (второй профиль/контакты/навыки на резюме, повтор языка, второе резюме на том же языке) |
| 413 | `REQUEST_TOO_LARGE` | тело больше лимита |
| 429 | `TOO_MANY_REQUESTS` | лимит запросов (по умолчанию 50 в секунду с одного адреса, всплеск 100) |
| 500 | `INTERNAL_ERROR` | ошибка сервера; ищите по `requestId` в логах |

`requestId` дублируется в заголовке ответа `X-Request-ID`.

**CORS.** Запросы с `Origin`, которого нет в списке разрешённых, получают `403` с пустым телом (актуально для `POST`/`PUT`/`DELETE` из браузера; `GET` без `Origin` проходит). Локальный Vite поэтому убирает `Origin` в прокси.

## Известные особенности контракта

- **Одно резюме на язык.** У пользователя не может быть двух резюме с одним `language` (`UNIQUE (user_id, language)`) — второе `POST /lk/resume` даёт `409`. Язык после создания не меняется.
- **Навыки — закрытый список.** `hardSkills`/`softSkills` принимают только значения справочника; собственные бэкенд отклоняет `400`.
- **Технологии — свободный текст.** Название хранится как есть; дублей по имени бэкенд не ищет.
- **Порядок записей.** Новые записи дописываются в конец. Порядок языков и технологий меняется отдельной ручкой `PUT …/order`; у остальных списков переставить записи нельзя.
