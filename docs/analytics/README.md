# Аналитика ссылок на резюме

Проект аналитики для именованных ссылок (`/cv/:linkId`). Источник требований — раздел «TODO: Аналитика» в [TODO.md](../TODO.md).

- [Бэкенд](backend.md): схема БД, классификация трафика, ручки сбора и отчётов, уведомления.
- [Фронтенд](frontend.md): трекер на публичной странице, вкладка «Аналитика» в кабинете.

## Что есть сейчас

- Таблица `resume_link_events` (`id`, `link_id`, `event_type`, `occurred_at`) с двумя типами: `view` и `contact_view`.
- `view` пишется на **каждый** успешный `GET /api/v1/cv/:linkId`, `contact_view` — на каждый успешный `POST /api/v1/cv/:linkId/contact-views`.
- `GET /api/v1/lk/link/:linkId/statistics` отдаёт два числа: `{ views, contactViews }`.
- На фронте вкладка «Аналитика» и трекер на публичной странице уже написаны и работают на моках (`VITE_MOCK_ANALYTICS=true`); реальные данные появятся, когда бэкенд реализует ручки из [backend.md](backend.md).

Проблемы текущей схемы: перезагрузка страницы = новый просмотр; владелец, открывший свою ссылку, накручивает счётчик; нельзя отличить одного посетителя от пяти; нет устройства, времени и глубины просмотра.

## Принципы

1. **Сырые события, агрегаты при чтении.** Пишем факты, считаем при отдаче отчёта. Объёмы маленькие (десятки–сотни визитов на ссылку), поэтому `GROUP BY` по индексу `(link_id, occurred_at)` хватит на годы; материализованные агрегаты не нужны.
2. **Визит — главная единица.** Каждая загрузка страницы получает `viewId` от сервера, все клиентские события привязываются к нему. Для резюме список визитов («вчера в 14:03, мобильный, 2 мин, дошёл до опыта, раскрыл Telegram») полезнее любых графиков, поэтому лента визитов — центральный экран аналитики.
3. **Помечаем, а не выбрасываем.** Боты и владелец сохраняются с флагом, отчёты их исключают. Если классификатор ошибся, можно пересчитать.
4. **Сервер — источник истины для важного.** Просмотр и раскрытие контакта фиксирует сервер в момент выдачи данных, клиент подделать или потерять их не может. Клиент отвечает только за поведенческие сигналы: время, скролл, клики, уход.
5. **Никаких персональных данных в сыром виде.** IP не храним, только хеш с суточной солью. User-Agent не храним целиком, только категории (устройство, браузер, ОС). Подробнее — в [бэкенде](backend.md#приватность).

## Важная особенность: SPA и превью-боты

Страница резюме — SPA. Telegram, LinkedIn, Slack и прочие при вставке ссылки скачивают **HTML-оболочку** через Caddy и JS не исполняют, поэтому до `GET /api/v1/cv/:linkId` они не доходят и просмотр не создают. Значит, основной мусор в API — это:

- боты, исполняющие JS (Googlebot, headless-сканеры, антивирусные «песочницы» почтовых сервисов);
- сам владелец;
- перезагрузки страницы.

Эвристика из TODO «один IP открыл все секции за 50 мс» к нам неприменима: все секции приходят одним запросом. Вместо неё работает сигнал «визит подтверждён живым JS» (см. «прочтения» в [бэкенде](backend.md#классификация-трафика)).

## Термины

| Термин | Что это |
|---|---|
| **Открытие** (`open`) | Успешный `GET /cv/:linkId`, не бот и не владелец. |
| **Прочтение** (`read`) | Открытие, по которому пришёл клиентский батч, а вкладка была видимой ≥ 5 с. Главная метрика «на резюме реально смотрели». |
| **Посетитель** (`visitor`) | Браузер с cookie `cv_vid`. Если cookie нет, берём пару (хеш IP, хеш UA) за сутки. |
| **Визит** (`view`) | Одна загрузка страницы, у него есть `viewId`. |
| **Вернувшийся** | Посетитель, у которого визиты были в два и более разных дня. |

## Открытые вопросы

1. **Канал уведомлений:** Telegram-бот или e-mail? Проект исходит из Telegram (быстрее доходит, не нужен SMTP), e-mail можно добавить позже как второй адаптер.
2. **Часовой пояс для графика по дням:** брать из браузера (параметр `tz`) или хранить в профиле? Проект исходит из параметра `tz`.
3. **Срок хранения:** события — 12 месяцев, клики — 90 дней. Подходит?
4. **Определение владельца** опирается на ту же аутентификацию, что и `/lk` (сейчас она моковая, `X-Mock-User-ID`). Когда появится настоящая сессия, проверка «это владелец» заработает без изменений схемы, но до этого момента флаг `is_owner` будет ставиться только в dev.
