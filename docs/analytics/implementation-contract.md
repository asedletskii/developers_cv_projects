# Аналитика: обязательный implementation contract

Этот документ дополняет `backend.md`. Он не вводит новую функциональность: его задача — зафиксировать правила, которые должны одинаково пониматься backend и frontend при реализации.

## 1. Жизненный цикл визита

- Успешный `GET /api/v1/cv/:linkId` активной опубликованной ссылки создаёт ровно один `resume_link_views` и получает новый `viewId`.
- `viewId` генерирует только сервер и возвращает через `X-View-Id`.
- Если запись визита не удалась, публичный `GET` всё равно может вернуть резюме; `X-View-Id` не возвращается, а frontend не отправляет события.
- `pagehide` завершает визит. Возврат из bfcache (`pageshow.persisted`) продолжает тот же `viewId`.
- Новый `GET` после reload/нового открытия — новый визит.

## 2. Идентификация посетителя

- При наличии cookie `__Secure-cv_vid` / `cv_vid` backend использует UUID из неё.
- Cookie ставит только backend. Frontend её не читает и не передаёт в JSON.
- Если cookie недоступна, применяется `UUIDv5(namespace, ip_hash || ua_hash || date)`.
- Такой fallback стабилен только внутри одних суток. На следующий день без cookie получается новый `visitor_id`.
- `visitor_id` никогда не возвращается владельцу резюме и не принимается из клиентского batch.

## 3. Источник истины

`resume_link_views` — единственный источник истины для:

- `views`;
- `reads`;
- `uniqueVisitors`;
- `returningVisitors`;
- дневной статистики.

Старое `resume_link_events(event_type = 'view')` допускается только для обратной совместимости. Оно не должно участвовать в новых агрегатах, иначе один GET может быть посчитан дважды.

`resume_link_events` остаётся источником клиентских событий (`section_view`, `download`, `tech_filter`, `external_click`, `print`, `contact_copy`, `contact_click`) и серверного `contact_view`.

## 4. Трафик и метрики

Классификация при GET выполняется в порядке:

1. `owner`;
2. `bot`;
3. `suspect`;
4. `human`.

Основные пользовательские отчёты считают только `human`.

`read` — это `human`-визит, для которого сервер получил состояние `active_ms >= 5000`.

`owner`, `bot` и `suspect` не удаляются из сырых данных: они нужны для диагностики фильтра и отображаются только там, где это явно предусмотрено контрактом.

## 5. Layout snapshot

При создании визита backend сохраняет:

```json
{
  "order": ["about", "experience", "skills", "projects", "contacts"],
  "hashes": {
    "about": "9f2c41aa7d31b204",
    "experience": "03be77d1c2a54e19"
  }
}
```

`hashes` — первые 8 байт SHA-256, представленные 16 hex-символами.

Исторический `max_section` интерпретируется только через `layout.order` конкретного визита. Текущая раскладка резюме не переписывает прошлые визиты.

## 6. Click-map

Клиент отправляет координаты внутри конкретной секции:

- `x_pct`: 0..10000, слева направо;
- `y_pct`: 0..10000, сверху вниз;
- `viewport_w`: фактическая ширина viewport.

`viewport_w` нужен только для определения breakpoint (`xs`, `md`, `lg`). Он не является системой координат.

`layout_hash` клика backend определяет сам из snapshot визита; frontend его не отправляет.

## 7. Время и идемпотентность

- `at` клиента используется только для порядка событий внутри одного batch.
- Время аналитического события — серверное `occurred_at`.
- `client_event_id` обеспечивает идемпотентность.
- `state` применяется монотонно: `active_ms` не уменьшается, `max_section` не возвращается назад, `final` завершает визит.

## 8. Ошибки и деградация

Аналитика не должна ломать публичную страницу резюме.

- Ошибка записи визита → отдаём резюме без `X-View-Id`.
- Ошибка/потеря клиентского batch → визит остаётся валидным, просто часть поведенческих данных отсутствует.
- Невалидные отдельные события отбрасываются; валидные события того же batch продолжают обрабатываться.
- Недействительная/выключенная ссылка использует существующие `404`/`410` и не создаёт визит.

## 9. Privacy contract

В аналитическую БД не записываются:

- исходный IP; для суточного HMAC IPv6 предварительно нормализуется до `/64`, IPv4-mapped IPv6 приводится к IPv4;
- полный User-Agent;
- полный URL referrer;
- содержимое контактов;
- `visitor_id` в ответах кабинета.

Хранятся только категории устройства/браузера/ОС, host referrer и суточно-псевдонимизированный IP hash.

Фраза для публичной страницы должна описывать это как статистику без персональных данных посетителя; юридическая квалификация по 152-ФЗ согласуется отдельно.

## 10. Что считать финальным контрактом

Если реализация противоречит этому документу или соответствующему разделу `backend.md`, нельзя исправлять расхождение локально в коде: сначала уточняется документация, затем меняется реализация и тесты.
