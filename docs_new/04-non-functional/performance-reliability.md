# Производительность и надёжность

## Производительность (NFR-PERF)

| ID | Требование | Метрика и цель | Проверка | Сейчас | Статус |
|---|---|---|---|---|---|
| NFR-PERF-01 | Публичная страница быстро открывается с телефона | Core Web Vitals, p75 по реальным визитам: **LCP ≤ 2,5 с**, **INP ≤ 200 мс**, **CLS ≤ 0,1**. Лабораторно (Lighthouse, эмуляция Moto G Power + Slow 4G): Performance ≥ 85 | Lighthouse CI на PR для `/cv/<тестовая ссылка>`; RUM через `web-vitals` в батч аналитики ([FR-ANL-006](../03-functional/FR-ANL.md)) | Не измеряется. Маршруты грузятся лениво (`lazy`), GSAP и анимации в основном бандле | План |
| NFR-PERF-02 | API отвечает быстро | Время обработки на сервере (гистограмма `request_duration_seconds`): `GET /cv/:linkId` — **p95 ≤ 150 мс, p99 ≤ 400 мс**; чтение в кабинете — p95 ≤ 200 мс; сохранение секции — p95 ≤ 300 мс | Дашборд Prometheus; алерт NFR-OBS-04 | Метрика собирается, цели не зафиксированы и не отслеживаются | Частично |
| NFR-PERF-03 | Один инстанс выдерживает пиковую нагрузку | **100 rps** на `GET /cv/:linkId` и 20 rps на запись в кабинете одновременно на 2 vCPU / 4 ГБ при соблюдении NFR-PERF-02 и 0 % ошибок | Нагрузочный тест k6 перед релизом с изменениями схемы или запросов публичной проекции | Не проводился | План |
| NFR-PERF-04 | Фронтенд не раздувается | Начальный JS публичной страницы ≤ **250 КБ gzip**; кабинет и редактор — отдельные чанки, не загружаются на публичной странице | `size-limit` в CI фронтенда | Разделение по маршрутам есть; бюджет не контролируется | Частично |
| NFR-PERF-05 | Отчёты аналитики не деградируют на реальных объёмах | До **10 000** пользователей, 50 ссылок на резюме, **100 000** визитов на ссылку: любой отчёт кабинета p95 ≤ 500 мс | Интеграционный тест с синтетическими данными; `EXPLAIN ANALYZE` запросов отчётов | Отчётов пока нет | План |
| NFR-PERF-06 | Уведомления приходят быстро | От события до отправки в Telegram — p95 ≤ **30 с** | Метрика задержки outbox (`created_at` → `sent_at`) | Уведомлений пока нет | План |
| NFR-PERF-07 | Сервер защищён от медленных клиентов и не блокирует ответ побочной работой | Таймауты: чтение 10 с, заголовки 5 с, запись 15 с, простой 60 с. Запись события аналитики не задерживает ответ больше чем на 2 с и не влияет на его код | Конфиг `HTTP_*_TIMEOUT`; юнит-тест `recordLinkEvent` | Как в требовании | Реализовано |

## Надёжность и доступность (NFR-REL)

| ID | Требование | Метрика и цель | Проверка | Сейчас | Статус |
|---|---|---|---|---|---|
| NFR-REL-01 | Публичная страница и API доступны | **SLO 99,5 %** успешных ответов `/ready` и `GET /cv/:linkId` за календарный месяц (≈ 3,6 ч простоя). Бюджет ошибок исчерпан — фича-релизы останавливаются до стабилизации | Внешний uptime-мониторинг раз в минуту | Мониторинга нет | План |
| NFR-REL-02 | Деплой почти не заметен пользователям | Простой при деплое ≤ **60 с**; запросы во время перезапуска получают ответ или `502` от Caddy, а не обрыв соединения | Ручная проверка при деплое; uptime-мониторинг | `docker compose up -d` пересоздаёт контейнер бэкенда — простой на время старта. Корректная остановка по SIGTERM есть | Частично |
| NFR-REL-03 | Сбой побочной подсистемы не ломает основной сценарий | Ошибка записи аналитики, уведомлений, внешних проверок не меняет ответ публичной страницы и раскрытия контакта | Юнит-тесты обработчиков с падающим рекордером | Аналитика — так; остальное появится позже | Реализовано |
| NFR-REL-04 | Данные восстанавливаются после катастрофы | **RPO ≤ 24 ч**, **RTO ≤ 4 ч**. Копии вне сервера, зашифрованы; восстановление проверяется раз в квартал | Отчёт о проверке восстановления | Бэкапов нет: потеря диска сервера = потеря всех данных | План |
| NFR-REL-05 | Данные остаются согласованными | Инварианты домена (владение, обязательные поля, уникальность, форматы ссылок) продублированы ограничениями БД (`CHECK`, `UNIQUE`, `FK … ON DELETE CASCADE`). Сохранение секции — одна транзакция | Интеграционные тесты на testcontainers PostgreSQL, тест отката транзакции | Как в требовании | Реализовано |
| NFR-REL-06 | Параллельные изменения не теряются молча | Любое изменение резюме и ссылки — через оптимистичную блокировку по версии; «последний выигрывает» недопустим | Интеграционные тесты `412` | Как в требовании | Реализовано |
| NFR-REL-07 | Контейнеры поднимаются после сбоя | `restart: unless-stopped` для долгоживущих сервисов; healthcheck PostgreSQL и NATS; бэкенд стартует только после здоровой БД и успешных миграций | `docker-compose.prod.yml` | Как в требовании | Реализовано |
