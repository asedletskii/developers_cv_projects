# EP-OPS. Эксплуатация

**Цель эпика:** сервис выкатывается без ручных шагов, его состояние видно, данные не теряются.

---

### US-OPS-01. Автоматический деплой

**Must** · **Реализовано** · P4 Оператор

Как оператор, я хочу, чтобы каждый коммит в `main`, прошедший проверки, автоматически выкатывался на сервер, чтобы не делать ручных шагов.

```gherkin
Сценарий: Успешный деплой
  Когда в main попадает коммит
  Тогда CI запускает для бэкенда gofmt, golangci-lint, go vet, тесты, govulncheck, сборку и проверку compose-файлов
  И для фронтенда — ESLint, проверку типов, Jest и сборку
  И при успехе собирает образы, публикует их в GHCR, копирует на сервер compose-файл и миграции и перезапускает стек

Сценарий: Упала проверка
  Когда любая проверка падает
  Тогда образы не публикуются и деплой не запускается
```

**Требования:** FR-OPS-001 – FR-OPS-003, NFR-MNT-03.

---

### US-OPS-02. Миграции при деплое

**Must** · **Реализовано** · P4 Оператор

Как оператор, я хочу, чтобы миграции БД применялись автоматически перед стартом бэкенда, чтобы код и схема не расходились.

```gherkin
Сценарий: Новая миграция
  Когда в деплое есть новая миграция
  Тогда сервис migrations применяет её до запуска бэкенда
  И бэкенд стартует только после успешного завершения миграций

Сценарий: Миграция упала
  Тогда бэкенд не запускается с новой версией, ошибка видна в логах сервиса migrations
```

**Требования:** FR-OPS-004, NFR-MNT-05.

---

### US-OPS-03. Проверка живости и готовности

**Must** · **Реализовано** · P4 Оператор

Как оператор, я хочу иметь ручки живости и готовности, чтобы оркестратор и мониторинг понимали состояние сервиса.

```gherkin
Сценарий: Сервис жив
  Когда запрошен GET /health
  Тогда ответ 200 {"status":"ok"} без обращения к зависимостям

Сценарий: БД недоступна
  Дано PostgreSQL недоступен
  Когда запрошен GET /ready
  Тогда ответ 503 {"status":"not_ready","checks":{"postgres":"failed"}}
```

**Требования:** FR-OPS-010, FR-OPS-011.

---

### US-OPS-04. Метрики и трассировка

**Should** · **Реализовано** · P4 Оператор

Как оператор, я хочу собирать метрики запросов и трассы, чтобы видеть нагрузку, задержки и узкие места.

```gherkin
Сценарий: Метрики
  Дано PROMETHEUS_ENABLED=true
  Когда запрошен GET /metrics
  Тогда отдаются счётчик запросов, гистограмма длительности и число запросов в обработке в формате Prometheus

Сценарий: Трассы
  Дано OTEL_ENABLED=true
  Тогда каждый HTTP-запрос создаёт span, экспортируемый по OTLP
```

**Требования:** FR-OPS-012, FR-OPS-013, NFR-OBS-02, NFR-OBS-03.

---

### US-OPS-05. Найти запрос в логах

**Must** · **Реализовано** · P4 Оператор

Как оператор, я хочу по ID запроса из экрана ошибки найти все записи лога этого запроса, чтобы разобрать обращение пользователя.

```gherkin
Сценарий: Ошибка у пользователя
  Дано пользователь прислал скриншот с «ID запроса: c16dd04d-…»
  Когда оператор ищет этот ID в JSON-логах
  Тогда находит запись с методом, шаблоном маршрута, статусом, длительностью и IP клиента
  И при включённой трассировке — trace_id и span_id для перехода к трассе
```

**Требования:** FR-OPS-014, NFR-OBS-01.

---

### US-OPS-06. Резервные копии и восстановление

**Must** · **План** · P4 Оператор

Как оператор, я хочу ежедневные резервные копии БД с проверенным восстановлением, чтобы не потерять данные пользователей при сбое диска или ошибке миграции.

```gherkin
Сценарий: Ежедневный бэкап
  Тогда раз в сутки создаётся дамп PostgreSQL и выгружается вне сервера
  И хранятся 7 ежедневных и 4 еженедельных копии

Сценарий: Учения
  Когда раз в квартал оператор восстанавливает последний бэкап на отдельном стенде
  Тогда сервис поднимается на восстановленных данных за время не больше RTO
```

**Требования:** FR-OPS-020, NFR-REL-04.

---

### US-OPS-07. Алерты

**Should** · **План** · P4 Оператор

Как оператор, я хочу получать алерт при недоступности сервиса или росте ошибок, чтобы узнавать о проблеме раньше пользователей.

```gherkin
Сценарий: Рост 5xx
  Дано доля ответов 5xx больше 1 % за 5 минут
  Тогда оператору приходит алерт в Telegram

Сценарий: Недоступность
  Дано внешняя проверка /ready падает 3 раза подряд с интервалом в минуту
  Тогда приходит алерт
```

**Требования:** FR-OPS-021, NFR-OBS-04.

---

### US-OPS-08. Защита от перегрузки

**Must** · **Частично** · P4 Оператор

Как оператор, я хочу ограничивать частоту запросов и размер тела, чтобы один клиент не мог положить сервис.

```gherkin
Сценарий: Частота
  Дано лимит 50 запросов в секунду с IP, всплеск 100
  Когда клиент превышает лимит
  Тогда он получает 429 TOO_MANY_REQUESTS

Сценарий: Размер тела
  Когда тело запроса больше 1 МиБ
  Тогда ответ 413 REQUEST_TOO_LARGE
```

**Требования:** FR-API-020, FR-API-021, NFR-SEC-06.

**Комментарий.** Лимит частоты работает по `ClientIP()`. Если `HTTP_TRUSTED_PROXIES` не указывает на Caddy, все запросы видны с одного адреса прокси, и лимит становится общим на всех посетителей ([GAP-07](../06-gaps-and-risks.md#расхождения)).
