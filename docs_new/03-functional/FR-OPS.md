# FR-OPS. Эксплуатация

Истории: [EP-OPS](../02-user-stories/EP-OPS.md).

## Топология прода

```
Интернет ──443/80──▶ Caddy (frontend-контейнер: статика SPA + reverse_proxy /api/*, авто-HTTPS)
                          │
                          ▼
                     backend:8080 (Go, read-only FS, cap_drop ALL)
                          │
            ┌─────────────┼──────────────┐
            ▼             ▼              ▼
      PostgreSQL 17    MinIO          NATS (JetStream)
                     (не используется) (не используется)
      migrations (migrate/migrate) — одноразовый сервис перед стартом backend
```

## Требования

### Поставка

| ID | Требование | Приоритет | Статус | Комментарий |
|---|---|---|---|---|
| FR-OPS-001 | CI на каждый push в `main` и каждый PR: бэкенд — `gofmt`, golangci-lint, `go vet`, `go test`, govulncheck, `go build`, проверка обоих compose-файлов; фронтенд — ESLint, `tsc --noEmit`, Jest, `vite build` | Must | Реализовано | `.github/workflows/ci.yml` |
| FR-OPS-002 | На `main` после зелёных проверок образы бэкенда и фронтенда публикуются в GHCR | Must | Реализовано | |
| FR-OPS-003 | Деплой: CI копирует на сервер `docker-compose.prod.yml` и `backend/db/migrations`, затем выполняет `pull` и `up -d`. Секреты сервера лежат только в `.env` на сервере | Must | Реализовано | Секреты GitHub — `DEPLOY_*` |
| FR-OPS-004 | Миграции применяются сервисом `migrations` до старта бэкенда; бэкенд стартует только при успешном завершении миграций и здоровом PostgreSQL | Must | Реализовано | `depends_on: condition` |
| FR-OPS-005 | Образы помечаются SHA коммита в дополнение к `latest`; `IMAGE_TAG` позволяет откатиться на предыдущий SHA одной переменной | Should | Частично | Теги формирует `docker/metadata-action`; процедура отката не описана |

### Состояние и наблюдаемость

| ID | Требование | Приоритет | Статус | Комментарий |
|---|---|---|---|---|
| FR-OPS-010 | `GET /health` — `200 {"status":"ok"}` без проверки зависимостей (liveness) | Must | Реализовано | |
| FR-OPS-011 | `GET /ready` — проверяет зависимости (сейчас PostgreSQL) и отвечает `200 {"status":"ready","checks":{...}}` или `503 {"status":"not_ready","checks":{"postgres":"failed"}}` | Must | Реализовано | |
| FR-OPS-012 | `GET /metrics` (при `PROMETHEUS_ENABLED=true`) — метрики в формате Prometheus: число запросов, гистограмма длительности, запросы в обработке | Should | Реализовано | `platform/telemetry/metrics.go`. Эндпоинт не должен быть доступен снаружи — см. NFR-SEC-09 |
| FR-OPS-013 | При `OTEL_ENABLED=true` каждый HTTP-запрос создаёт span и экспортирует его по OTLP gRPC на `OTEL_EXPORTER_OTLP_ENDPOINT` | Should | Реализовано | |
| FR-OPS-014 | Каждый запрос логируется одной JSON-записью: `request_id`, метод, шаблон маршрута, статус, длительность, IP клиента, при трассировке — `trace_id`, `span_id`. `X-Request-ID` принимается от клиента или генерируется | Must | Реализовано | `middleware/logger.go`, `requestid` |

### Данные и реагирование

| ID | Требование | Приоритет | Статус | Комментарий |
|---|---|---|---|---|
| FR-OPS-020 | Ежедневный логический дамп PostgreSQL с выгрузкой вне сервера (S3-совместимое хранилище в другом ЦОД), шифрование, ретенция 7 ежедневных и 4 еженедельных копий, ежеквартальная проверка восстановления | Must | План | NFR-REL-04 |
| FR-OPS-021 | Внешняя проверка `/ready` раз в минуту и алерты в Telegram оператору: недоступность 3 проверки подряд, доля 5xx > 1 % за 5 минут, p95 длительности > 1 с за 10 минут, заполнение диска > 80 % | Should | План | NFR-OBS-04 |
| FR-OPS-022 | Корректная остановка: по SIGTERM сервер перестаёт принимать новые соединения и дожидается текущих запросов до `HTTP_SHUTDOWN_TIMEOUT` (10 с) | Must | Реализовано | |
