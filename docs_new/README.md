# developers-cv.ru — требования к продукту

Полное описание сервиса в виде пользовательских историй (US), функциональных (FR) и нефункциональных (NFR) требований. Документ отражает состояние ветки `main` на 2026-09-30 (коммит `44e9e48 fix: links routes`) и планы из [TODO](../docs/TODO.md) и [проекта аналитики](../docs/analytics/README.md).

**Источник истины — код.** Если требование со статусом «Реализовано» расходится с кодом, ошибка в документе: исправьте его в том же PR, что и код. Известные расхождения собраны в [gaps-and-risks.md](06-gaps-and-risks.md).

## Соглашения

### Идентификаторы

| Тип | Формат | Пример | Правило |
|---|---|---|---|
| Эпик | `EP-<ДОМЕН>` | `EP-LNK` | домен из таблицы ниже |
| Пользовательская история | `US-<ДОМЕН>-<NN>` | `US-LNK-03` | номер не переиспользуется после удаления |
| Функциональное требование | `FR-<ДОМЕН>-<NNN>` | `FR-LNK-012` | нумерация с шагом 1; вставка — следующий свободный номер, а не `012a` |
| Нефункциональное требование | `NFR-<КАТЕГОРИЯ>-<NN>` | `NFR-SEC-04` | категории — в [04-non-functional](04-non-functional/README.md) |
| Расхождение / риск | `GAP-<NN>`, `RISK-<NN>` | `GAP-03` | в [06-gaps-and-risks.md](06-gaps-and-risks.md) |

Домены:

| Код | Домен |
|---|---|
| `ACC` | Доступ к кабинету и профиль пользователя |
| `RES` | Резюме как сущность: создание, статус, удаление, версии |
| `EDT` | Редактор содержимого резюме |
| `DSG` | Оформление и структура публичной страницы |
| `PUB` | Публичная страница резюме |
| `CNT` | Контакты и защита от сбора |
| `LNK` | Именованные ссылки на резюме |
| `ANL` | Аналитика просмотров |
| `NTF` | Уведомления |
| `OPS` | Эксплуатация |
| `API` | Общие правила HTTP API |

### Статусы

| Статус | Значит |
|---|---|
| **Реализовано** | Есть в `main` на бэке и фронте (или там, где требование применимо), покрыто тестами |
| **Частично** | Реализована часть: например, бэк без фронта, или без части сценариев. Что именно не сделано — в колонке «Комментарий» |
| **План** | Спроектировано или согласовано, кода нет |
| **Идея** | Кандидат в бэклог, решение о реализации не принято |
| **Не делаем** | Сознательно отклонено, причина указана |

### Приоритет (MoSCoW)

| Приоритет | Значит |
|---|---|
| **Must** | Без этого продукт не решает задачу или нарушает закон / безопасность |
| **Should** | Важно, но есть обходной путь |
| **Could** | Улучшение, делается при наличии ресурса |
| **Won't** | Не в этом горизонте планирования |

### Формулировки

- **FR** формулируются от лица системы: «Система должна …». Одно требование — одно проверяемое утверждение. Числа, форматы и коды ответов указываются явно.
- **US** — в формате «Как `<роль>`, я хочу `<действие>`, чтобы `<ценность>`» с критериями приёмки в виде сценариев «Дано / Когда / Тогда».
- **NFR** — с измеримой метрикой, целевым значением, способом проверки и текущим состоянием.

### Как вносить изменения

1. Новая функциональность начинается с US (что и зачем), затем FR (что делает система), затем, если нужно, NFR.
2. PR, реализующий требование, меняет его статус и ссылку на код в [трассировке](05-traceability.md).
3. Удалённое требование не стирается, а получает статус «Не делаем» с причиной.
